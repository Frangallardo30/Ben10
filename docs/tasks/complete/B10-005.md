# Guardar la fecha real de cada propuesta

## Estado

Hecha

## Pedido

La columna heredada `expires_at` se usa actualmente para ordenar el historial y se resta un día para mostrar la fecha de creación. El vencimiento automático ya está activo por B10-009: conviene separar su plazo de la fecha de creación.

## Criterios de aceptación

- [x] Las propuestas nuevas guardan `created_at` con la hora real de creación.
- [x] Las propuestas existentes conservan su fecha visible y su orden en el historial.
- [x] La migración se puede repetir sin duplicar ni perder datos.
- [x] `/historial` muestra la fecha correcta para registros nuevos y anteriores.

## Implementación

Las propuestas nuevas guardan `created_at` al crearse y calculan `expires_at` como esa fecha más 24 horas. Una reentrega conserva ambas fechas. Historial y perfil ordenan por creación con desempate por ID descendente; el historial muestra directamente `created_at`.

`src/proposal-dates.js` comprueba la columna antes de añadirla. Si otra instancia gana el ALTER, verifica el esquema antes de continuar. Completa solo fechas nulas con `expires_at - 86400` y crea el índice de historial después; no cambia vencimientos, estados ni votos. Los fallos permiten reintentar. Las lecturas usan la fecha heredada si aún no hay columna y COALESCE si existe pero alguna fila sigue sin migrar. No esperan la preparación de escrituras.

El esquema inicial incluye la columna para bases nuevas. El índice se crea en la migración para que reaplicar `schema.sql` sobre una base antigua no falle por la columna ausente.
